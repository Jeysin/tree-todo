## 0. 版本修订：v1 → v2 重做了什么

v1 方案在三个根本判断上走偏了，v2 全部推翻重做：

| # | v1 的判断 | v2 的判断 | 影响面 |
|---|---|---|---|
| 1 | 入口复用「统计」tab | **「统计」是文档级、热力图是全局级，语义不同源，不能共用**；重构整个应用布局，新增全局层「总览」 | §3 全章重写 |
| 2 | 在每个文档库内建 `completion_ops` / `completion_items` 事件账本，靠同库事务保强一致 | **全局库 `global.db` 统一存放；不建事件账本，改为可重算的物化聚合；不强一致，最终一致** | §4 全章重写 |
| 3 | 双口径：默认「显式完成项数」，可切「含级联叶子」 | **唯一口径：当日完成的叶子节点数**。父节点是分类，永不计数 | §2、§5 新增 |

v1 保留下来的部分：网格几何、色阶 token 的「四处都要写」坑、分位数分档、可访问性基线、时区处理思路。这些与入口和存储无关，仍然成立。

### 0.1 v2.1 产品决策（已确认，覆盖文中一切「建议 / 待定」表述）

| # | 决策点 | 最终结论 | 对方案的影响 |
|---|---|---|---|
| 1 | 「统计」是否改名「进度」 | **不改名**，继续叫「统计」 | `ViewMode` 保留 `'stats'`；只新增 `'overview'`；`04-ui-ux-design.md` 快捷键表不需要改名 |
| 2 | 删除已完成任务是否保留历史 | **不保留**，历史数字下降 | 维持「当前仍存在的叶子」口径，不引入 `leaf_done_ledger` |
| 3 | 回收站文档是否计入 | **不计入**；移入回收站即视为全部任务已删除，数字下降；**从回收站恢复后立即重新计入** | 同步只扫描活动文档；文档进回收站时删除其聚合行；恢复时重算 |
| 4 | 默认统计范围 | **全部文档（不含回收站）** | 查询去掉 `includeTrashed` 开关，回收站在数据层就被排除，不存在「可选计入」 |
| 5 | 日界 | **00:00** 固定 | `day_start_hour = 0`；不做 UI 配置项，仅保留 meta 字段 |

> 决策 3 的实现要点：回收站里的文档文件仍然存在，但同步服务**不扫描 `trash/`**，并在每次对账时删除「不在活动文档集合内」的聚合行。因此「进回收站 → 数字下降」「恢复 → 数字回来」都由同一条重算规则自然得到，不需要两套逻辑。

## 1. 决策摘要

| 问题 | 结论 | 一句话理由 |
|---|---|---|
| **入口放哪** | 侧栏顶部新增**导航区**「总览」（含今日完成数徽标）；点击后主区切换到全局视图，侧栏保持可见 | 侧栏是唯一的跨文档器官，天生属于全局层；热力图要一整块横向空间（标准档 686px），只有主区放得下 |
| **「统计」怎么办** | **保留原名「统计」**，作为文档级视图；在顶栏加上当前文档名做作用域提示 | 产品已确认不改名；作用域区分靠「文档名 + tab 组」与「侧栏导航」，不靠改名 |
| **数据存哪** | 新增全局数据库 `app_data_dir/global.db`，独立版本号，与文档库解耦 | 用户明确要求一块可扩展的全局数据区；文档库 schema 保持 v4 不动，零迁移风险 |
| **怎么保证一致** | **最终一致**：脏标记（延迟优化）+ 防抖重算 + 指纹对账（正确性兜底）；查询前 flush 保证「读己之写」 | 热力图是回顾性数据，秒级延迟不可感知；用跨库事务换强一致收益为负 |
| **数什么** | **当日完成的叶子节点数**。父节点是分类，不进任何计数；唯一口径，无切换 | 叶子才是待办本体，这是产品一直以来的模型（`docs/03` §3.4） |

| **范围** | 默认**全部活动文档**；回收站文档一律不计入 | 产品已确认；见 §4.8 |
| **代价** | 删除已完成的叶子、或把文档移入回收站 → 历史格子的数字会下降 | 与「数当前存在的叶子」自洽；撤销（100 步内）可恢复。见 §5.3 |

## 2. 产品理念：叶子是任务，父节点是分类

这一条是 v2 一切计算的地基，必须先钉死。

### 2.1 定义

| 概念 | 定义 | 是不是待办 |
|---|---|---|
| **叶子节点** | 没有任何子节点的节点 | ✅ **是**。唯一的一种待办任务 |
| **父节点（容器）** | 至少有一个子节点的节点 | ❌ 不是。它是分类 / 分组 / 目录，本身不是一件事 |

推论（直接写进计数规则）：

```text
任务总数     = 叶子节点数
已完成任务数 = status = 'done' 的叶子节点数
完成率       = 已完成叶子数 / 叶子数
```

父节点的 `status` 是**聚合展示状态**（不变量 I2：子树全部完成 ⇒ 父节点 done），作用是「一眼看出这个分类下还有没有没做完的事」，**不进入任何任务计数**。

### 2.2 各出口的一致性要求

| 出口 | 现状 | 是否已经只数叶子 |
|---|---|---|
| 平铺视图（`FlatView`） | 只列叶子 | ✅ |
| 状态栏（`StatusBar`） | `pending` / `done` / 完成率都按叶子算 | ✅ |
| 统计页（`StatsView`） | 按叶子 | ✅ |
| 热力图（本次新增） | 按叶子 | ✅ |
| 导出摘要 / 通知 / 周报（未来） | — | **必须只数叶子** |

结论：现有实现已经符合这条理念，只是从未被写成硬约束。本次把它升格为红线。

### 2.3 边界情况（必须在实现前想清楚）

| 场景 | 按「叶子是任务」会发生什么 | 是否可接受 |
|---|---|---|
| 勾选一个含 12 个叶子的父节点（M2 级联） | 12 个叶子变 done → 当天 **+12**；父节点自己不计 | ✅ 符合直觉：「我今天清掉了 12 件事」 |
| 勾选最后一个 pending 叶子 → 父节点自动 done（CC2） | 只有那 1 个叶子计入，父节点不计 | ✅ 避免重复计数 |
| 一个已完成叶子下新增了子节点 | 它变成父节点，从任务集合中退出 → 当天数字 -1 | ⚠️ 可接受。它已经不是「一件事」而是「一组事」了 |
| 删除一个已完成的叶子 | 物理删除 → 当天数字 -1 | ⚠️ 见 §5.3，需要 UI 说明 + 撤销兜底 |
| 粘贴 / 导入带 done 状态的子树 | 叶子被还原，按其**原始** `completed_at` 归属历史日期 | ✅ 搬运既有数据不会污染今天 |
| 文档移入回收站 | 该文档全部日期从热力图移除 → 数字下降 | ✅ 产品决策 3：回收站 = 已删除 |
| 文档从回收站恢复 | 重新扫描该文档 → 数字立即回来 | ✅ 同一套重算规则，无特判 |

### 2.4 落到 `AGENTS.md`

本轮已更新 `AGENTS.md`（见文末 §10），新增：

- 「项目是什么」增加核心心智模型一段；
- 领域红线新增第 10 条「叶子是任务，父节点是分类」。

红线原文要点：所有「任务数 / 完成数 / 完成率 / 统计 / 热力图 / 导出摘要」的计数**只数叶子**，禁止把父节点计入任务总量或完成量；M2 级联只是「一键把该分类下的叶子全部标记完成」的便捷操作，不改变任务总数。

## 3. 布局重构（重点一）

### 3.1 现状诊断

当前骨架（`src/App.tsx`）：

```
┌─ Sidebar ─┬─────────────── TopBar ────────────────┐
│  文档树    │ [树形][平铺][统计]          ⋯  ⌨       │
│           ├───────────────────────────────────────┤
│           │              main（五选一）             │
│           ├───────────────────────────────────────┤
│ 🗑   ⚙    │ 12 待处理 · 34 已完成 · 完成率 74%      │
└───────────┴───────────────────────────────────────┘
```

四个结构性问题：

1. **两个层级被压平成三个平级 tab**。`树形` / `平铺` 是「同一份数据的不同渲染」，`统计` 是「这份数据的分析」——三者**都是当前文档的**，但 UI 上没有任何作用域提示。用户（包括本次反馈）会自然地以为「统计」是全局的。
2. **侧栏只承担文件管理，不承担信息架构**。侧栏是应用里唯一的跨文档器官，却只有一个文档树 + 两个工具图标。回收站、设置这类全局入口被塞在最底部的无标签图标里，和文档树不在同一个语义层。
3. **没有「家」**。启动直接进上次打开的文档，没有一个「看一眼全貌」的地方。任务管理工具恰恰需要俯瞰视角来建立节奏感。
4. **tab 组会随功能膨胀**。如果每个新视图都加 tab，3 → 4 → 5，最终顶栏变成一排互不相关的按钮。

### 3.2 目标信息架构

把应用显式拆成两层：

```
┌─ 全局层（跨文档） ────────────────────────────┐
│  总览 · 回收站 · 设置                          │
├─ 文档层（当前文档） ──────────────────────────┤
│  树形 · 平铺 · 统计                            │
└───────────────────────────────────────────────┘
```

| | 全局层 | 文档层 |
|---|---|---|
| 数据范围 | 全部文档聚合 | 当前文档 |
| 导航载体 | **侧栏导航区**（常驻、带标签） | **顶栏 tab 组**（带文档名前缀） |
| 代表视图 | 总览（热力图） | 树形 / 平铺 / 统计 |

分层的判据很简单：**换个文档还成立的视图，属于全局层；换个文档就变的视图，属于文档层。**

### 3.3 候选方案与评分

| # | 方案 | 具体落位 |
|---|---|---|
| **A** | **侧栏顶部导航区** ✅ | 侧栏 header 下加一行「总览」，与文档树分区；点击切主区 |
| B | 左侧图标栏（Activity Rail） | 窗口最左再加 48px 竖条，放总览 / 回收站 / 设置 |
| C | 顶栏一级模式切换 | 顶栏最左加「文档 / 总览」分段控件，右侧才是文档 tab |
| D | 「总览」作为虚拟文档 | 文档树顶部插入一条特殊条目 |
| E | 独立窗口 | 新 `WebviewWindow`，可做常驻挂件 |

评分（1–5，越高越好；「改动成本」分高 = 便宜）：

| 维度 | 权重 | A 侧栏导航 | B 图标栏 | C 顶栏切换 | D 虚拟文档 | E 独立窗口 |
|---|---|---|---|---|---|---|
| 全局语义清晰度 | 25% | 5 | 4 | 4 | 2 | 4 |
| 可扩展性（后续全局数据） | 20% | 5 | 4 | 3 | 2 | 3 |
| 空间成本（高 = 不额外占） | 15% | 5 | 2 | 5 | 5 | 3 |
| 发现性 | 15% | 4 | 4 | 5 | 5 | 3 |
| 改动成本 | 15% | 4 | 3 | 3 | 2 | 1 |
| 对现有信息架构的侵入 | 10% | 4 | 3 | 2 | 1 | 3 |
| **加权总分** | 100% | **4.60** | **3.45** | **3.75** | **2.80** | **2.95** |

**A 胜出的三个理由**：

1. 侧栏本来就是「所有文档的列表」——它天生是全局的。把全局视图挂在它上面，语义零成本；挂在顶栏（C）则要在一个已经装着文档 tab 的横条里再造一层作用域，认知负担更高。
2. 图标栏（B）要永久吃掉 40–48px 宽度，在 800px 最小窗口下相当于砍掉 6% 可用宽度，而它承载的只是 3 个入口——信息密度太低。
3. 虚拟文档（D）会污染文档模型：它不能重命名、不能删除、不能导出、不能进回收站，每个文档操作都要特判一次。

### 3.4 推荐方案：侧栏升级为「导航栏」

侧栏从「文件列表」升级为三段式导航：

```
┌────────────────────────┐
│ ◆ Tree Todo      v2.1  │  ← 品牌区（不变）
├────────────────────────┤
│ ▦  总览             +3 │  ← ① 导航区（新增，常驻）
├────────────────────────┤
│ 文档               +   │  ← ② 内容区（现有文档树，不变）
│  📁 工作               │
│    📄 产品规划         │
│    📄 竞品分析         │
│  📄 生活               │
│                        │
├────────────────────────┤
│ 🗑 2           ⚙       │  ← ③ 工具区（不变）
└────────────────────────┘
```

- **① 导航区**：一行 `LayoutDashboard` 图标 + 「总览」+ 右侧今日完成数徽标。视觉上与文档树用 1px 分隔线隔开，选中态复用文档行的样式（`bg-accent/12`）。
- **② 内容区**：完全不动，现有拖拽 / 右键菜单 / 重命名全部保留。
- **③ 工具区**：完全不动。

**选中态唯一性（v2.1.0）**：侧栏**同一时刻只允许一处高亮**，即「当前页」只有一个。
全局层（总览 / 回收站 / 设置）停在导航区或工具区的高亮上，文档树里**任何行都不高亮**；只有处于文档层（树形 / 平铺 / 统计）时，当前文档行才高亮。
实现上不再为「选中文档」另存一份状态：文档行高亮直接由 `currentDocId` 推导，`Sidebar` 本地的 `selectedFolderId` 只表示「新建落点」（选中目录时让位、不高亮文档），进入全局层即清空。这样两份状态不可能各自为真、同时变蓝。

**今日徽标规则**：`+N` 仅在 `N > 0` 时显示（accent 底色小胶囊）；`N = 0` 时不显示任何东西。「每天可见」由「总览入口常驻」保证，不靠一个 `+0` 制造噪音。

**C. 全局层（设置 / 回收站）**：与现状一致，只是顶栏不再显示文档 tab 组。

三个关键设计点：

1. **顶栏加文档名**（`📄 产品规划`）。这是消除「统计是不是全局的」歧义的最低成本手段——它把「下面三个 tab 属于这份文档」变成视觉事实。文档名超过 120px 时截断，`title` 给全名。
2. **明细面板常驻在右列**，默认显示今天，点击格子切换日期。避免「点开才出现、默认一片空白」的空洞感，也让「今天做了什么」零点击可见。
3. **状态栏在全局面换成全局信息**：`总览 · 5 个文档 · 刚刚同步`。既避免在全局页展示文档级数字造成新的语义错乱，又顺带把「数据是派生的」这件事轻量地告诉用户。

### 3.6 导航模型

`ViewMode` 保持扁平联合类型（**只加一个成员**），把分层表达在常量数组里，避免大规模重构：

```ts
// src/stores/todoStore.ts

/** 文档层：换个文档就变的视图。 */
export const DOC_VIEWS = ['tree', 'flat', 'stats'] as const;
/** 全局层：跨全部文档的视图。 */
export const GLOBAL_VIEWS = ['overview', 'trash', 'settings'] as const;

export type DocView = (typeof DOC_VIEWS)[number];
export type GlobalView = (typeof GLOBAL_VIEWS)[number];
export type ViewMode = DocView | GlobalView;
```

- `'stats'` **保留原名**（产品决策 1），只新增 `'overview'`。
- 新增 `lastDocView: DocView`：从全局层回到文档层时恢复上次用的渲染方式（当前实现是硬编码回 `'tree'`，见 `Sidebar.tsx` L862）。
- `previousViewMode`（设置页「返回」）→ 改为 `previousViewMode: ViewMode`，语义不变。

行为约定：

| 操作 | 结果 |
|---|---|
| 点侧栏「总览」 | `setViewMode('overview')`，当前文档不变 |
| 总览页点某个文档的明细条目 | `switchDocument(id)` + `setViewMode(lastDocView)` + `revealNode(nodeId)` |
| 全局层下点任意文档 | `switchDocument(id)` + `setViewMode(lastDocView)` |
| 文档层下点「利润」→ 设置 | 记住 `previousViewMode`，返回时回到原视图 |
| 重启应用 | 恢复**上次停留的页面**：`viewMode / lastDocView / previousViewMode` 落到 `localStorage['tree-todo.viewState']`，启动即读；当前文档仍由后端 `lastOpened` 决定，两者互不影响 |

> 为什么不在启动时固定回文档树：在总览核对完直接关窗口是常见动作，下次被塞回某个文档会显得「没记住事」。恢复的是**视图**，不是一次性的滚动位置或选中的日期——后者属于瞬时状态，重启后仍回到默认值。

## 4. 全局数据区（重点二）

### 4.1 目标与非目标

**目标**

1. 一块**独立、可扩展**的全局存储区，不与任何文档库耦合；
2. 热力图查询在 5ms 量级返回，不随文档数线性变慢；
3. **可以随时整体删除而不丢任何用户数据**——这是缓存/物化视图的本质属性，也是「最终一致」能成立的前提；
4. 后续新增全局数据（跨文档搜索索引、标签统计、周报）不必再动架构。

**非目标**

- ❌ 不做事件溯源 / 审计日志（本期不需要，见 §4.2）；
- ❌ 不做跨设备同步（远期）；
- ❌ 不把 `documents.json` 迁进 SQLite（索引文件工作良好，迁移只会引入风险）。

### 4.2 决策变更：为什么不再做事件账本

v1 的事件账本是**为了对抗「双口径 + 快照漂移」**：一次勾父节点会让 13 个节点同时 done，得靠 `target_count` / `leaves_completed` 两个字段区分口径，还得靠 `op_id` 把撤销和事件关联起来。

改成「**只数叶子**」之后，这些需求全部消失了：

| v1 需要事件账本解决的问题 | 叶子口径下的表现 |
|---|---|
| 勾父节点算 1 还是 12 | 恒等于「该操作让多少个叶子变成 done」，不需要人选择 |
| CC2 向上传播把父节点也算一次 | 父节点不是叶子，天然不计 |
| 撤销要让数字回退 | 撤销后节点回 pending、`completed_at` 清空，重算即回退 |
| 粘贴 / 导入带回 done 节点 | 按其原始 `completed_at` 归入历史，不污染今天 |

于是可以做一次减法：**不建事件表，改为「文档库是真相源、global.db 是可重算的物化聚合」**。

| 维度 | 事件账本（v1） | 物化聚合（v2） |
|---|---|---|
| 写入路径 | 业务事务内双写 | 事务外异步重算 |
| 对领域核心的侵入 | 改 `history.rs` 加 `op_id`，改所有 command | **零侵入**：只读文档库，不参与任何写事务 |
| 文档库 schema | v4 → v5，要迁移 + 备份 + 校验 | **保持 v4 不变** |
| 数据损坏 | 不可重建（唯一真相） | **删掉重建即可** |
| 增量正确性 | 靠调用点不漏写 | 靠指纹对账，漏标也能自愈 |
| 能力边界 | 能记「做过又取消」 | 只记「当前仍然是完成的」 |

最后一行是唯一的真实损失，处理方式见 §5.3，并在 §11 作为待拍板项交给产品决定。

> 如果你的判断是「做过的事就该永久留下」，那就在 `global.db` 里加一张 `leaf_done_ledger`（append-only），由**文档库历史表**回放填充，与本方案的主链路完全解耦——加它不影响这里任何一个设计，只是把 §5.3 的行为从「会下降」改成「不下降」。

### 4.3 文件布局

```
app_data_dir/
├── documents.json          # 现有：文档 / 目录索引（不变）
├── docs/{doc_id}.db        # 现有：文档库，schema v4（不变）
├── trash/…                 # 现有：回收站（不变）
└── global.db               # 新增：全局数据区（可随时删除）
    ├── schema_version      # 全局库自己的版本，与文档库解耦
    ├── meta                # KV：时区快照、日界、最后重建时间
    ├── doc_sync            # 每个文档的同步水位与指纹
    └── leaf_done_daily     # 核心：文档 × 本地日期 → 叶子完成数
```

两条硬规则：

1. **`global.db` 不存任何用户原始数据**，只存可从文档库重算出来的派生值。删掉它 → 下次启动自动重建，用户无感。
2. **文档库 schema 不动**（保持 `CURRENT_SCHEMA = 4`）。全局库有独立的 `schema_version` 表与独立的 `GLOBAL_SCHEMA` 常量。

### 4.4 Schema（`GLOBAL_SCHEMA = 1`）

```sql
PRAGMA journal_mode = WAL;

CREATE TABLE IF NOT EXISTS schema_version (version INTEGER NOT NULL);

-- 全局 KV：时区快照、日界、最后重建时间、诊断信息
CREATE TABLE IF NOT EXISTS meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
) WITHOUT ROWID;

-- 每个文档的同步水位
CREATE TABLE IF NOT EXISTS doc_sync (
    doc_id      TEXT PRIMARY KEY,
    fingerprint TEXT NOT NULL,          -- "节点数:done数:max(updated_at)"
    synced_at   TEXT NOT NULL,          -- UTC RFC3339
    state       TEXT NOT NULL,          -- ok | trashed | missing | error
    note        TEXT                    -- 失败原因 / 跳过原因
) WITHOUT ROWID;

-- 核心：文档 × 本地日期 → 当日完成的叶子数
CREATE TABLE IF NOT EXISTS leaf_done_daily (
    doc_id     TEXT NOT NULL,
    local_date TEXT NOT NULL,           -- YYYY-MM-DD（本地时区）
    leaf_count INTEGER NOT NULL,
    PRIMARY KEY (doc_id, local_date)
) WITHOUT ROWID;

CREATE INDEX IF NOT EXISTS idx_leaf_daily_date ON leaf_done_daily(local_date);
```

设计说明：

- **不设外键**：`doc_id` 指向 `documents.json` 里的条目，不是 SQLite 表；且文档彻底删除时由同步服务显式清理。
- **`local_date` 存字符串**：日期比较是字典序，索引可直接用于 `BETWEEN`；同时避免 SQLite 解析 `chrono` 输出的 9 位小数秒（`2026-11-14T09:44:09.123456789+00:00` 不是 SQLite 的合法时间格式，**禁止在 SQL 里对 `completed_at` 用 `date()`**）。
- **`WITHOUT ROWID`**：这两张表都是纯 KV 形态，省一层 B-tree。
- **`meta` 预置键**：`tz_offset_min`（上次全量重算时的时区偏移）、`day_start_hour`（日界，默认 0）、`last_full_rebuild_at`、`schema_created_at`。

### 4.5 计数查询：叶子完成数怎么算

对单个文档做一次全量分组（重算的原子单位就是「一个文档」）：

```sql
-- ① 取该文档所有「仍是 done 的叶子」的完成时间
SELECT n.completed_at
  FROM nodes n
 WHERE n.status = 'done'
   AND n.completed_at IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM nodes c WHERE c.parent_id = n.id);
```

`idx_nodes_parent` 已存在（`db/mod.rs` L248），`NOT EXISTS` 走索引，万级节点下单次扫描约 2–5ms。

```rust
// ② 在 Rust 侧按本地日期归桶（不在 SQL 里做时间运算）
let mut buckets: BTreeMap<String, i64> = BTreeMap::new();
for ts in rows {
    let dt = DateTime::parse_from_rfc3339(&ts)?.with_timezone(&Local);
    let day = (dt - Duration::hours(day_start_hour)).format("%Y-%m-%d").to_string();
    *buckets.entry(day).or_insert(0) += 1;
}
```

```sql
-- ③ 整体替换该文档的聚合行（global.db 单库事务，原子）
BEGIN IMMEDIATE;
DELETE FROM leaf_done_daily WHERE doc_id = ?1;
INSERT INTO leaf_done_daily(doc_id, local_date, leaf_count) VALUES (?,?,?);  -- 循环
UPDATE doc_sync SET fingerprint = ?2, synced_at = ?3, state = 'ok' WHERE doc_id = ?1;
COMMIT;
```

跨文档查询：

```sql
SELECT local_date, SUM(leaf_count) AS n
  FROM leaf_done_daily
 WHERE local_date BETWEEN ?1 AND ?2
   AND doc_id IN (…scope 内的文档…)     -- 全部文档时省略此条件
 GROUP BY local_date;
```

> `delete + insert` 而不是 `upsert`：这样「某天的数字归零」会被正确删除，不会留下 `leaf_count = 0` 的僵尸行。一次重算写入的行数 = 该文档有完成记录的天数（通常 < 200），成本可忽略。

### 4.6 一致性契约

不强一致，但要**把承诺写清楚**，否则「最终一致」等于「不知道什么时候对」：

| 编号 | 承诺 | 保证手段 |
|---|---|---|
| **C0 · 有界陈旧** | 运行期相对文档库最多落后「防抖窗口（≤ 1s）+ 一次重算（≤ 50ms）」；未打开的文档不会变化，天然一致 | 防抖 worker |
| **C1 · 读己之写** | 用户完成一个任务后打开总览，**必定**看到新数字 | 查询前 `flush()`：对当前文档做指纹校验 + 重算 |
| **C2 · 崩溃收敛** | 强杀 / 断电导致落后，下次启动对账后收敛 | 启动全量指纹对账 |
| **C3 · 幂等可重建** | 任意时刻 `rebuild` 的结果与增量结果逐行相同；`global.db` 可整体删除后重建 | 重算只依赖文档库，不依赖历史 |
| **C4 · 永不阻塞** | 同步失败绝不影响、不阻塞、不回滚任何用户操作 | 同步在独立线程，写失败只记日志 |

关键点：**脏标记只是延迟优化，不是正确性依赖**。正确性由「文档库指纹对账」保证——即使某个新加的 command 忘了标脏，`flush()` 与后台巡检也会发现并修正（见 §4.7）。

### 4.7 同步管线

```
          ┌──────────────────────────────────────────────────┐
用户操作 → │ command 提交成功                                  │
          │   └─ stats.mark_dirty(doc_id)   ← 仅内存 HashSet，O(1)│
          └──────────────────────────────────────────────────┘
                              │ 通知
                              ▼
          ┌──────────────────────────────────────────────────┐
          │ StatsWorker（独立线程，持 global.db 连接）          │
          │   wait → sleep 600ms（防抖，合并连续操作）          │
          │   for doc in dirty: recompute(doc)                │
          └──────────────────────────────────────────────────┘
                              │
                              ▼
   ┌─────────────────────────────────────────────────────────┐
   │ 读路径 get_overview / get_overview_today                 │
   │   1. flush()：处理脏集合 + 指纹校验当前文档               │
   │   2. 查 leaf_done_daily → 聚合 → 计算 KPI/连续天数        │
   └─────────────────────────────────────────────────────────┘

   ┌─────────────────────────────────────────────────────────┐
   │ 后台巡检（每 8s，仅在窗口可见时）                          │
   │   指纹校验「当前文档」；变化则重算                          │
   └─────────────────────────────────────────────────────────┘
```

三个设计要点：

1. **worker 只监听「当前文档」**。应用是单窗口、一次只打开一个文档，非当前文档不可能在运行期被修改（导入除外，导入会显式标脏新文档）。所以后台巡检只需要盯一个文档，成本 = 每 8s 一次索引扫描。
2. **`flush()` 不依赖脏集合**。它直接对当前文档跑指纹 SQL；指纹不等就重算。这样即使调用点漏标，C1 仍然成立。
3. **worker 的文档库连接用 `PRAGMA query_only = ON`**。不用 `SQLITE_OPEN_READ_ONLY`（WAL 库以只读标志打开需要 `-shm` 可写，容易报 `SQLITE_READONLY`），而是正常打开 + 强制只读，双保险。

**指纹 SQL**（单条，走全表但极快，10k 节点约 1–3ms）：

```sql
SELECT COUNT(*),
       COALESCE(SUM(status = 'done'), 0),
       COALESCE(MAX(updated_at), '')
  FROM nodes;
```

拼成 `"{count}:{done}:{max_updated_at}"`。任何增删、状态变更、重命名都会改变这三项之一（每个变更都会刷新 `updated_at`，且它成为新的 `MAX`）。

**脏标记调用点**（性能优化，非正确性必需，尽力覆盖）：

| 位置 | 原因 |
|---|---|
| `commands/nodes.rs`：`create_node` / `update_node` / `delete_node` / `toggle_status` / `paste_nodes` / `move_node` | 可能增删叶子或改变完成状态 |
| `commands/agent.rs`：`accept_run` / `accept_node` | Agent 验收会置 done |
| `commands/io.rs`：`import_bundle` | 新导入的文档需要首次重算 |
| 文档操作：`delete_document` / `restore_document` / `purge_document` | 状态变为 `trashed` / 恢复重算 / 删除行 |

> **不需要标脏**：`set_collapsed` / `expand_nodes` / `collapse_all` / `switch_document` / 搜索 / 主题切换——它们不改变叶子集合与完成状态。

### 4.8 对账与自愈

**启动对账**（后台线程，不阻塞窗口显示）：

```text
docs = documents.json 的 documents（**活动文档，不含回收站**）
for doc in docs:
    fp = fingerprint(doc)              # 打不开 → state='error'，跳过
    if doc_sync[doc].fingerprint != fp:
        recompute(doc)                 # 内部 delete+insert 一个事务
    sleep(30ms)                        # 让出 IO，避免启动抖动
purge_non_active(active_doc_ids)       # 回收站 / 已删除文档的聚合行一并清掉
```

- **回收站文档：完全不扫描**。对账只遍历 `documents.json` 的 `documents`（活动文档）；每次对账结束时执行一次「清理不在活动集合内的聚合行」，把已进回收站的文档行删掉。**这就是决策 3 的全部实现**——数字会下降，且不需要监听「谁进了回收站」。
- 文档从回收站恢复：`restore` 成功后该文档重新出现在 `documents` 里，下一次对账（恢复命令内同步触发一次）重算并写回，数字立即回来。
- 文档彻底删除：同上，行本来就已经被清理，`purge` 只需再清一次 `doc_sync`。
- 启动对账期间 `global.db` 可能只有部分文档是最新的，查询结果带 `stale: true`，UI 不显示错误，只在状态栏右端显示「同步中」。
- `DocStore::trash_dir()` 不在同步服务的可见范围内：服务只接受 `docs_dir()` 下的路径，从结构上避免误扫回收站。

**全量重建**触发条件：

| 触发 | 说明 |
|---|---|
| `global.db` 不存在 | 首次启动，建库 + 重建 |
| 打开失败 / `quick_check` 失败 | 重命名为 `global.db.corrupt-{ts}` 后重建 |
| `schema_version > GLOBAL_SCHEMA` | 用户回退到旧版：不猜、不降级，提示「全局数据由新版本创建，可重建」 |
| `tz_offset_min` 与当前时区不一致 | 历史日期归属会变，必须全部重算 |
| `day_start_hour` 被修改 | 同上 |
| 设置页「重建统计数据」 | 用户手动触发 / 客服排查 |

**多实例**：Tauri 未启用单实例插件，理论上可能双开。`global.db` 与文档库都用 `busy_timeout(5s)`，冲突时退化为一方失败并重试；最坏情况是短暂数字不一致，下次对账自愈。若要彻底避免，后续引入 `tauri-plugin-single-instance`（不在本方案范围）。

### 4.9 失效矩阵

| 场景 | 用户看到什么 | 何时恢复 |
|---|---|---|
| 完成操作后立刻打开总览 | 数字已更新 | 同步 `flush()`（C1） |
| 完成操作后停在树里 | 徽标 600ms 内更新 | 防抖 worker |
| 重算时崩溃 | 旧数据完整（单库事务） | 下次启动对账 |
| `global.db` 写入失败（磁盘满） | 数字偏旧，无报错弹窗 | 磁盘恢复后巡检自愈 |
| `global.db` 损坏 | 总览页提示「正在重建统计…」 | 自动重建完成（秒级） |
| 文档移入回收站 | 该文档全部日期从图上消失 | 回收站命令内同步对账 |
| 文档从回收站恢复 | 数字回来 | 恢复命令内同步对账 |
| 文档彻底删除 | 该文档的历史数字消失 | 立即 |
| 系统时区变化 | 短暂旧值 | 下次启动/切总览时全量重建 |
| 时钟回拨 | 可能短暂错位 | 指纹不变则不影响（日期由 `completed_at` 推） |

### 4.10 性能预算

| 操作 | 规模假设 | 预估 | 实测要求 |
|---|---|---|---|
| 单文档重算 | 1 万节点 | 3–8ms | < 30ms |
| `get_overview`（111 天） | 50 文档 | < 3ms | < 15ms |
| `get_overview`（371 天） | 50 文档 | < 5ms | < 20ms |
| `flush()` 指纹校验 | 1 万节点 | 1–3ms | < 10ms |
| 启动全量对账 | 50 文档 | 0.3–1s（后台） | 不阻塞首屏 |
| 存储占用 | 371 天 × 50 文档 | ≈ 750KB | < 5MB |

不做进程内缓存：一次查询就是个位数的毫秒，缓存只会引入第二份真相。

## 5. 计数口径与语义边界

### 5.1 唯一口径

> **某日完成数 = 该日（本地时区）完成、且此刻仍然是「已完成叶子」的节点数。**

只有一个口径，UI 不提供切换。这直接消解了 v1 里最麻烦的「1 还是 12」的争议——按叶子算，答案唯一。

### 5.2 各类操作的表现

| 操作 | 当天数字 | 说明 |
|---|---|---|
| 勾选一个叶子 | +1 | |
| 勾选含 12 个 pending 叶子的父节点 | +12 | 级联让 12 个叶子变 done；父节点不计 |
| 勾选含 12 个叶子、其中 5 个已 done 的父节点 | +7 | 只数**本次状态发生变化**的叶子 |
| 完成最后一个叶子 → 父节点自动 done | +1 | 父节点不重复计 |
| `Ctrl/⌘+Z` 撤销完成 | −N | 重算自动回退 |
| 取消完成（`uncomplete`） | −1 | |
| 完成后删除该叶子 | −1 | 见 §5.3 |
| 粘贴 / 导入带 done 的子树 | 0（今天） | 按原始 `completed_at` 归入历史 |
| 拖拽 / 重命名 / 改备注 / 折叠 | 0 | 不影响叶子集合 |
| 文档进回收站 | 该文档全部日期清零 | 决策 3：回收站 = 已删除 |
| 文档从回收站恢复 | 该文档全部日期复原 | 与进回收站同一条重算规则 |
| 文档彻底删除 | 该文档全部日期清零 | 与进回收站结果相同（后者本来就已经清掉） |

### 5.3 已知语义边界（必须写进 UI 与文档）

「只数当前存在的叶子」带来两个可预期的行为，**不藏着**：

1. **删除一个已完成的叶子，当天数字会下降**。因为按定义它不再是一项存在的任务。撤销（100 步内）可恢复；退出应用后不可恢复。
2. **一个已完成的叶子新增子节点后，它退出计数**。它从「一件事」变成了「一组事」。

处理方式：

- 总览页标题旁一个 `ⓘ`，tooltip：「统计的是当前仍存在的叶子任务的完成时间；删除任务会让对应日期的数字减少。」
- 明细面板底部一行弱提示：「任务被删除后不再出现在这里。」
- 若产品判断「做过就该留下」，走 §4.2 末尾的 `leaf_done_ledger` 升级路径，不改本方案主链路。

### 5.4 日界与时区

- `completed_at` 是 UTC RFC3339；**日期归属在 Rust 侧用 `chrono::Local` 计算**，不在 SQL 里算。
- 一期日界固定 **00:00**；`meta.day_start_hour` 已预留，改成 4 点只需改一个常量 + 全量重建（**历史会一起变**，因为重算用的是同一套规则）。
- 时区变化（旅行 / 夏令时）：`meta.tz_offset_min` 与当前不一致 → 全量重建。语义是「按你现在的本地日历重新看这段历史」，而不是「冻结在当时的时区」。这条要写进 tooltip，否则跨时区的用户会觉得数字变了。
- 前端 `src/lib/heatmap.ts` 只处理 `YYYY-MM-DD` 字符串，**禁止** `new Date('2026-11-14')`（按 UTC 解析，东八区会少一天），统一用 `new Date(y, m-1, d)`。

### 6.3 刷新时机

| 触发 | 处理 |
|---|---|
| 进入总览 | `overviewStore.load()`；Rust 侧先 `flush()` |
| 完成 / 撤销 / 重做 / 验收 | `mark_dirty` → worker 更新 `leaf_daily`；侧栏徽标 600ms 内刷新；总览可见时发一次 `overview:changed` 事件让前端重查 |
| 切换文档 | 徽标不需要变（全局值）；总览若可见则重查（scope 不变） |
| 导入文档 | 对导入的每个 doc 标脏，worker 首次重算 |
| 删除 / 恢复文档、删除目录 | 命令内**同步**跑一次对账（活动文档集合变了，必须立即重算并清理聚合行） |
| 跨本地零点 | 前端 60s 定时器检测本地日期变化 → 重查 + 徽标归零 |
| 主题切换 | 只换 CSS token，不重查 |

### 6.4 错误与降级

| 情况 | 表现 |
|---|---|
| `global.db` 正在重建 | `stale: true`，总览页顶部一行「正在同步历史数据…」，热力图用已有数据先渲染 |
| 部分文档打不开 | `skippedDocs > 0`，页脚弱提示「N 个文档暂时无法读取」，不阻断 |
| 全部无数据 | 空态（§7.7），不是错误 |
| 查询异常 | 总览页「数据读取失败 · 重试」，其他视图不受影响；徽标隐藏 |
| `SchemaTooNew` | 保持现有启动报错行为，不做静默降级 |

## 7. UI / 视觉设计

### 7.1 总览页信息层级

1. **页头**：`总览` + 副标题（`全部文档的…`；选中某个文档时变成 `「文档名」的…`）+ 右侧两个筛选：**统计范围**（`DocPicker` 浮层面板：目录树 + 搜索，默认「全部文档」）与**时间范围**（近 12 个月 / 某个自然年）
2. **KPI 卡 4 个**：今年完成（范围内叶子数）、活跃天数、当前连续、最长连续（主区宽度 < 620px 时排成 2×2，避免标签折行）

#### 7.1.1 文档选择器（`DocPicker`）

原生 `<select>` 在「文档很多」时不成立：选项会变成几百行、macOS 把 `optgroup` 标签渲染成不可点的假选项（看起来像重复的文档）、且无法搜索。因此做成仿访达的浮层面板：

| 项 | 规格 |
|---|---|
| 触发按钮 | 只显示当前选择（`全部文档` / 文档名），`h-8` 与相邻筛选同高；超长名 `truncate`，`title` 给出完整路径 |
| 面板 | 320px 宽，`bg-elevated` + `shadow-2xl`，`position: fixed` 挂到 `body`（Portal），不受页面 `overflow` 裁剪；右对齐触发按钮，下方放不下自动翻到上方 |
| 内容 | 首行「全部文档」（含文档总数），其余为目录树：目录可展开/折叠，右侧显示该目录（含子目录）的文档数 |
| 展开策略 | 打开时只展开**当前选中文档的祖先目录**，其余折叠——文档再多也不会一次铺满；找具体文档用搜索 |
| 搜索 | 输入即过滤全部文档（不区分大小写），结果按侧栏顺序，每行显示名称 + 所属路径 |
| 键盘 | `↑↓` 移动、`←→` 折叠/展开目录、`↵` 确认、`Esc` 关闭；打开即聚焦搜索框 |
| 高度 | 上限 440px（约 11 行）。贴着内容高度会因亚像素余量触发一条几乎满高的滚动条，看着很脏；超限时才滚动 |
| 复用 | 组件只吃 `documents / folders / value / onChange`，不读 store；排序规则来自 `src/lib/docTree.ts`，与侧栏同一份实现（`compareDocSiblings`） |

### 7.2 网格几何与响应式

| 项 | 规格 |
|---|---|
| 网格 | 53 列 × 7 行；列 = 周（周一 → 周日），行 = 星期 |
| 格子尺寸 | 由容器宽度反推：`53×格子 + 52×间距 ≤ 容器宽 − 星期标签列 − 月份标签右溢`；上限 10px，下限 6px |
| 间距 | 优先 3px；排不下依次降到 2px、1px——先保格子边长，再收间隙 |
| 宽度预算 | 扣掉星期标签列 18px、月份标签右溢预留 24px（「12月」比单个格子宽，最后一列文字会向右溢出，这段同样计入滚动宽度） |
| 退化 | 「6px 格子 + 1px 间距」仍排不下（容器 < ~430px）才 `overflow-x-auto` 横向滚动 |
| 实测 | 1280×800 窗口（容器 936px）→ 10px/3px；800×600 最小窗口（容器 ≈436px）→ 6px/1px，整年一屏不滚动 |
| 标签 | 左侧「一 / 三 / 五」隔行；上方「1月 … 12月」，同月只在首列出现一次。标签比格子宽（「12月」≈26px），相邻月份会互相压住，因此**按列距避让**：首列若是上一年的残月（年视图从 12/29 开始）就丢弃它的标签，其余标签最小间隔 `ceil(28 / (格子+间距))`，不够则跳过——宁缺不叠 |
| 时间范围 | 默认「近 12 个月」（滚动窗口，尾部补到本周）；可切自然年（首尾周补白格 `outside`，不参与统计、不响应点击） |
| 年份选项 | 从**发布年**（`LAUNCH_YEAR = 2026`）推到今年，由当前日期推导，不逐年写死：2026 只有「2026 年」，2027 为「2027 / 2026」，之后每年多一个。发布年是唯一的事实常量，只影响选项下界 |
| 统计范围 | `DocPicker` 浮层面板（§7.1.1）：`全部文档` + 目录树 + 搜索。选中文档在该文档被删除 / 移入回收站后自动回落到「全部文档」，不停留在无效范围上 |
| 未来日期 | 不渲染（浅色占位边框），避免误读为「0 完成」 |
| 滚动 | 仅作兜底：默认滚到最右（最近一周） |

### 7.3 色阶 token（禁止组件硬编码色值）

在 `src/styles/globals.css` 新增 5 个 token，**四处都要写**（`:root` 浅色、`@media (prefers-color-scheme: dark)`、`:root[data-theme="light"]`、`:root[data-theme="dark"]`），否则显式主题下会串色；并在 `@theme inline` 暴露成 Tailwind 颜色类：

```css
  --heat-0: #ebedf0; --heat-1: #9be9a8; --heat-2: #40c463;
  --heat-3: #30a14e; --heat-4: #216e39;
}
/* 深色参考值（写入 dark 的两个块） */
--heat-0: #2d333b; --heat-1: #0e4429; --heat-2: #006d32;
--heat-3: #26a641; --heat-4: #39d353;

@theme inline {
  --color-heat-0: var(--heat-0);
  --color-heat-1: var(--heat-1);
  --color-heat-2: var(--heat-2);
  --color-heat-3: var(--heat-3);
  --color-heat-4: var(--heat-4);

```

- 组件只用 `bg-heat-0` … `bg-heat-4`；`heat-0` 同时承担「0 完成」与「空占位」，用 1px `border` 描边区分。
- 色相沿用 `success` 语义并做明度阶梯，不引入红绿涨跌语义（本功能与股票无关）。

### 7.4 分档算法（`src/lib/heatmap.ts`）

固定阈值（1/3/6/10）对新用户太陡、对重度用户又全是最深色。用**所选范围内的相对分位数**：

```text
counts = days.filter(d => d.leafDone > 0).map(d => d.leafDone)
若 counts 为空 → 全部 level 0
q  = quantile(counts, [0.25, 0.50, 0.75, 0.90])
t1 = max(1, q1)
t2 = max(t1 + 1, q2)
t3 = max(t2 + 1, q3)
t4 = max(t3 + 1, q4)          // 用 q90 而非 max，防单日极值压平其余
level(c) = 0 if c = 0 else c ≤ t1 ? 1 : c ≤ t2 ? 2 : c ≤ t3 ? 3 : 4
```

- 切换范围 / 年份时阈值随数据重算；图例「少 ▢▢▢▢▢ 多」不写具体数字，准确值走 tooltip。
- 严格递增化保证不会出现「两个档位同一个值」导致某档永不出现。

### 7.5 连续天数

- **当前连续**：从今天往前数连续 `leafDone > 0` 的天数；**今天为 0 不打断**昨天延续的段（早上打开应用看到 0 不至于挫败），从昨天起算。
- **最长连续**：所选范围内最长的连续段，不跨范围拼接。
- 两者都在 **Rust 侧计算**，与前端网格解耦（红线 3：前端不做统计计算）。

### 7.6 下钻与跳转

- 点格子 → 右列明细切到该日；当天无记录时显示「这天没有完成记录」。
- 明细行：`HH:mm` + 任务标题 + 文档名（弱化）。**不做「任务已删除」占位**——已删除的叶子本来就不在计数里，保持一致（§5.3）。
- 点明细行 → `switchDocument(docId)` → `setViewMode(lastDocView)` → 复用平铺视图现成的 `revealNode(id)`（展开祖先链 + 选中 + 滚入视口 + 短暂高亮）。
- `Esc` 关闭明细焦点；格子可 Tab 聚焦、方向键移动、`Enter` 查看当日明细。

### 7.7 文案

| 场景 | 文案 |
|---|---|
| 空态 | 「完成第一个任务后，这里会亮起第一格」+ 按钮「回到任务树」 |
| 同步中 | 「正在同步历史数据…」 |
| 口径（`ⓘ`） | 「统计的是当前仍存在的叶子任务的完成时间。父节点是分类，不计入；删除任务会让对应日期的数字减少。」 |
| 时区说明 | 「按你当前所在时区划分日期；更换时区后历史会重新归位。」 |
| 徽标 | `+3`；title「今天完成 3 个叶子任务 · 打开总览 (Ctrl/⌘+4)」 |
| 页脚 | 「总览 · 5 个文档 · 刚刚同步」/「2 个文档暂时无法读取」 |
| 降级 | 「数据读取失败 · 重试」 |

### 7.8 可访问性

- 每格 `role="gridcell"` + `tabIndex` + `aria-label="2026年11月14日，完成 3 个任务"`。
- 0 / 非零不只靠颜色区分：tooltip 有数字、`aria-label` 有文字、图例有档位。
- 焦点环用 `accent`，对比度满足 `04` §6 的 WCAG AA 基线。
- 动效克制：tooltip 淡入 ≤ 120ms、明细切换 ≤ 160ms；不做格子逐个入场动画。

## 9. 实施计划与风险

### 9.1 分阶段

| 阶段 | 内容 | 可独立合入 |
|---|---|---|
| **P0 · 全局数据区** | `global_db.rs` + `stats.rs` + 4 个 command + `mark_dirty` 调用点 + 启动对账 + R1–R17 单测。**纯后端，UI 不动** | ✅ 合入后无用户可见变化，零风险 |
| **P1 · 布局重构 + 总览首屏** | 侧栏导航区、`ViewMode` 分层、TopBar/StatusBar 适配、`OverviewView` + 热力图 + KPI 卡 + 色阶 token + 前端单测 | ✅ 用户可见的核心功能 |
| **P2 · 补体验** | 明细面板下钻与跳转、统计页口径统一（改调 `get_overview` with `scope=document`）、设置项（重建统计）、验收清单 | ✅ |

> 与 v1 最大的不同：**不需要「先埋点攒数据」**。因为口径是「当前叶子状态 + `completed_at`」，P1 上线当天就能算出完整历史（包括升级前的），不存在「第一天空白」的问题。

### 9.2 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 删除任务导致历史数字下降 | 用户觉得「我明明做过」 | `ⓘ` 明示口径 + 撤销兜底；必要时上 `leaf_done_ledger`（§4.2） |
| 漏标脏文档 | 数字短暂偏旧 | **不是正确性问题**：`flush()` 与 8s 巡检用指纹兜底（§4.6） |
| 布局重构影响既有导航 | 回归 | `ViewMode` 只增成员不做结构性改写；逐条跑 `07` 现有验收 |
| 大文档重算卡顿 | 操作后微卡 | 防抖 600ms + 后台线程 + 只重算单文档；1 万节点 3–8ms |
| `global.db` 与文档库版本错配 | 回退旧版后打不开 | 全局库独立版本 + 可重建；版本过高时明确提示而非静默 |
| 双开实例竞争写 | 短暂不一致 | `busy_timeout` + 对账自愈；后续可加 single-instance 插件 |
| 热力图被误读为「日程」 | 功能蔓延 | `01` §7 措辞收窄（§10） |
| 色阶 token 只写了两处 | 显式主题下串色 | §7.3 的「四处都要写」列为实现自查项 |
